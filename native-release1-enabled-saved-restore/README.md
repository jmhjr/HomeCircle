# Instrumented enabled saved-account partial restore

This is a prepared procedure for HomeCircle source
`91ae59106a661143b770d7a3564d363c7c11a7dd` and original 113-member ZIP
`004c9bc4a968ad395e18033837cb42f5bd1d8719a8d90fc778fd20be4ff08f97`.
Preparation and local contracts are not a successful native restore result.
The earlier [disabled-entry R6 result](https://github.com/jmhjr/HomeCircle/actions/runs/39697883468)
remains separate and unchanged.

The owned disposable guest must report actual Linux amd64 KVM, HAOS 18.3,
Core 2026.10.2, Supervisor 2026.10.3 and Python 3.14.6. No existing VM, everyday
Home Assistant, owner account, device passcode or real provider credential is
used. One push affecting this fixture or its exact workflow file on
`codex/native-amd64-validation` schedules the trial. There is no additional
dispatch trigger.

## Exact product bytes and early startup boundary

The original ZIP and inventory stay unchanged. Staging retains 112 runtime
members byte for byte. The sole product-file adaptation appends
`homecircle_safe_restore_qa` to `manifest.json` dependencies, using the
original JSON layout. Original and adapted manifest hashes are bound
separately. This qualifies an instrumented package only.

The dependency synchronously installs a QA fence before HomeCircle component
or config-entry runtime setup. An already-imported product module is permitted;
an already-set-up component/runtime refuses. Installation also refuses native
import failure, a second installation and nonempty proxy settings. A fixed
metadata-only startup failure record prevents an unexplained grant timeout.

Actual DirectFindMy and DirectLife360 classes construct real SDK clients from
SDK-valid fictional saved sessions and accessories. Find My's fictional remote
Anisette request is refused before DNS; reaching report HTTP is not required.
Life360 uses its real saved-token client and an actual new session. The fence
denies all that session's requests, all three Apple HTTP paths (legacy, bounded
onboarding and separate report transport), and other external aiohttp calls.
Only the fixed local Supervisor service and exact loopback card/original-image
GETs are forwarded. Redirects, explicit proxies and late ambient proxies refuse.

Fixed intact-hook counters must witness at least one Life360 and one Apple
transport invocation. Recovery-command, reservation-callback and recovery-HTTP
counters must all stay zero. Unexpected recovery commands or reservations are
counted and refused before their original operation. These are seam invocation
counts, not network-byte counts or successful provider authentication.

## Synthetic state and prepared dependencies

The stopped-Core seed writes one enabled HomeCircle entry with equal, nonempty
data/options, a real private Fernet key/vault pair and Life360 credentials in
actual config-entry storage. Four explicit registry joins bind two Find My
items and two tracker-only person-kind members. Checks preserve selection,
display/map settings, a saved place, account/session identity and a fixed
synthetic profile image. No Home Assistant Person entry is seeded.

Managed Core must load the exact source, restore an actual Find My session and
two saved reports, expose the real provider classes/four selected tracker
entities, and project the chosen member settings. The card and original image
must be served byte for byte over the bounded loopback paths. No movement or
fresh provider location is claimed.

Before the closed boot, a separate bounded step installs the manifest
requirements under actual Core constraints into its normal config-local
bootstrap library. The complete resolved closure is inventoried, excluding
only generated bytecode, with origins/versions checked. Ordinary requirement
checking stays enabled. Exact prepared library bytes must be in the backup and
each managed startup. This does not qualify a fresh consumer dependency install.

## Five phases and one default restore window

The phases are `baseline_enabled`, `mutated_enabled`,
`automatic_restored_enabled`, `repaired_storage_enabled` and
`restart_enabled`. The baseline persists a discriminating title-only update
through Home Assistant's API. Mutation changes saved configuration, credentials,
vault, selection/identity ledger and registry joins, advancing the fictional
guard from 2 to 3. The newest guard is retained outside the entire guest.

The real Supervisor partial backup must include the database, pair, both
config-entry snapshots, selections/joins, original image, adapted package,
prepared dependencies, complete QA helper and exact disposable configuration.
Archive inspection binds those bytes before opening the network; it does not
decrypt. Restore-barrier and one-use boot-grant files must be absent from the
archive and pre-window state.

Core is stopped before opening. The saved enabled mutated entry, package/helper,
inspected local archive, cached same-Core image and retained guard are rechecked.
Effective ignored conditions must be empty and persisted conditions empty or
absent. Foreign conditions refuse without writes. No jobs/options mutation or
unsupported override is used.

One QMP opening serves only Supervisor's ordinary restore conditions. An
independent positive control and at most 18 read-only network observations over
90 seconds must establish host/Supervisor internet readiness. The synchronous
partial restore runs once. A finally block attempts one bounded close even
after uncertain opening/restore responses. Confirmed closure, a negative
control, guest-agent availability and unchanged defaults are required within
the reserved 90-second cleanup period. There is no restore retry.

Enabled HomeCircle may load its vault and attempt polling during this window.
The early fence covers those attempts. A one-use process-bound grant gates QA
observation after verified closure; it does not delay product setup. A strictly
newer process and absent pre-restore barrier distinguish automatic restored
startup from stale archived receipts.

## Manual repair and qualification limits

The expected guard sequence is **2 → 3 → 2 → 3 → 3**: baseline, mutation,
automatic restored startup, explicit repair, restart. First restored startup
loads the older guard before repair. Zero recovery counters establish only
that startup did not invoke the instrumented recovery seams. They do not detect
backup rollback or block a later owner-initiated recovery in an ordinary install.

The controller then stops Core and imports the separately retained newest
guard. Its actual API must report the fictional identity blocked at 3. Four
bounded offline Core-image contexts execute exact Vault/identity/guard code
without the managed package initializer, retaining network-none isolation,
dropped capabilities, read-only roots, one private configuration mount, exact
stopped-Core ownership and cleanup. Post-repair contexts require unchanged
no-op pair bytes and the same 18 independently cloned fault cases. No real
recovery proof is sent.

Independent synthetic Recorder entities must show pre-backup rows restored,
post-backup marker rows removed and new post-restore rows surviving restart.
This is Recorder continuity evidence, not real provider history, movement,
source freshness or complete household acceptance.

A completed trial can qualify only
`instrumented_enabled_synthetic_restore_qualified`, with default Supervisor
conditions and explicit newest-guard repair. Ordinary/uninstrumented enabled
restore safety, automatic guard antirollback, real provider authentication or
renewal after restore, full-system/encrypted cloud backup, HACS acceptance and
stable release approval remain false. The ordinary restore-safety release gate
remains open.

The workflow verifies its frozen all-file hash map before importing fixture
code and requires the exact frozen contract count without skips. Success needs
saved-storage, guard-context and storage-context acceptance. Uploads permit
only six fixed JSON receipts: host and five phases. Raw credentials, vaults,
ledgers, archives, images, coordinates, private workspaces and unfiltered logs
are excluded.
