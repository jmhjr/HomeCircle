# Direct Life360 development candidate

This document records the beta 11 candidate checks completed before publication. Beta 10 read Home Assistant entities supplied by another integration. Beta 11 retains that route and adds two choices:

1. Select an existing device tracker as a person, without creating an HA Person record.
2. Enter Life360 account credentials in HomeCircle. The backend discovers Circle members and creates HA device trackers. Reopen Options once they appear and select the intended members.

## Implementation boundary

The direct connector uses `life360==7.2.0`, the client used by the current [Life360 custom integration](https://github.com/pnbruckner/ha-life360). It accepts password or Bearer token authorization. Life360's API is undocumented and can delay Circle/member discovery or rate limit requests; the maintainer documents both behaviors. HomeCircle checks credentials before saving, polls only when direct connection is enabled, pauses after rate limiting, marks trackers unavailable after a sustained outage, and clears its timers/session on unload. It keeps no separate location history and does not project credentials or raw addresses to the card.

HA config entry storage holds the credential. HomeCircle does not set a Recorder exclusion; HA Recorder settings determine whether direct tracker states and locations are retained. The account form tells users to review those settings before connecting. The current setup needs two saves when a new account is connected: connect it first, wait for entities, then select people under Options. Options reports whether tracker discovery is pending or how many trackers are available. Discovery repeats periodically after an initial success, so a new Circle member can appear without an HA restart. Each member's successful report is tracked independently; one healthy member cannot hide another member's extended polling failure. Existing Person and tracker selections remain available. Replacing an expired password or token is available from the household screen.

An authorization rejection now starts Home Assistant's reauthentication repair flow. Options and the sanitized diagnostics export distinguish authorization, rate limits, network failure, provider errors, unexpected response shapes, and partial member failures. See the [provider issue workflow](TRACKER-PROVIDER-ISSUES.md). Credential replacement also updates the older saved entry data so an obsolete secret is not retained there. New connections save a hash of the verified account ID in private HA config storage; reconnect and credential replacement reject a different verified account. Older development entries without that hash compare old and new accounts when the old sign-in still works; otherwise, keeping the household requires explicit same-account confirmation. A saved direct tracker is restored as unavailable during an offline startup until fresh discovery succeeds.

## Validation completed

- Fictional account and API tests cover setup, initial and periodic tracker discovery, per-member outage behavior, rate-limit pause, unexpected response classification, sanitized diagnostics, reauthentication, source projection, credential replacement, and real HA platform creation/unload.
- The disposable HA UI showed the direct account form with both authorization methods. No real Life360 credential was entered.
- The same disposable UI created a person directly from a fictional `device_tracker`, with no Person record, and Home Assistant confirmed the configuration.
- The full Python and frontend suites, static checks, package lifecycle, and public-file privacy guard passed for this candidate.
- The published beta 10 ZIP matched its recorded SHA-256. A saved fictional Person household survived replacement with the earlier development candidate and a separate-process restart. That rehearsal checked the candidate package without rewriting it. This did not publish a release.
- On 2026-10-03, a read-only in-memory check used the existing authorized Life360 connection from the mounted Home Assistant configuration. HomeCircle's direct client authenticated, discovered multiple Circle members, polled them, and projected every discovered tracker as available. The credential, names, IDs, coordinates, and raw responses were not copied into this repository or printed. No Home Assistant configuration was changed. This verifies current service acceptance of the direct client at that moment, but it is not an installed-in-HA or movement test.
- A separate disposable Home Assistant test on 2026-10-03 used that same authorization in memory. The actual HomeCircle config flow verified the credential, created five Life360 tracker entities, and reported all five available. One tracker was selected as a person through Options and appeared in the normalized household. The disposable HA fixture used fictional zones and was removed after the test; the live HA configuration was not changed. The one-off test file was removed from the development tree after the run.
- A follow-up live read on 2026-10-03 found report times on all five available trackers. All five timestamps parsed as nonfuture values within 24 hours of the check. This verifies report-time projection from the provider response, not actual movement timing.
- A disposable two-process Home Assistant test on 2026-10-03 connected the same account, selected one tracker as a person, stopped Core, and restarted Core using the saved disposable storage. Both processes loaded the HomeCircle entry, exposed five available trackers, retained the selected member, and projected its report time as tracker evidence. The second process read only its saved disposable configuration. The temporary storage and one-off script were removed after the test; the live server was not changed.
- A disposable reauthentication test on 2026-10-03 first connected the authorized account and selected one tracker. It then replaced the credential only in disposable Home Assistant storage with a known-invalid test token and reloaded the entry. Life360 rejected that token, HomeCircle reported `auth_required`, and Home Assistant opened exactly one reauthentication flow. Submitting the existing valid token through that flow reloaded the entry with five available trackers and preserved the selected member. This verifies provider rejection and repair with real API responses; it does not reproduce a naturally expired token. The live server was not changed.
- A fictional external Life360 tracker and a HomeCircle direct tracker coexist in the disposable HA tests with distinct entity IDs. Setup shows a warning about duplicate trackers and requests when the external source is present. This confirms coexistence in HA; it does not measure requests from two live integrations running against the same account.
- The beta 11 card shows fixed provider connection messages to admins and clears them after recovery. The snapshot gives non-admin viewers no provider status. Fictional websocket and card tests cover the access boundary and repair-message lifecycle; the live server's card was not changed.
- The card now also marks the account setup as unfinished when direct trackers are available but no tracker from that account is explicitly selected, even if the household already has other members. The admin prompt points to HomeCircle Options and clears after a HomeCircle-owned tracker is chosen. Tests distinguish an existing external tracker, an active HA Person source, and an explicit HomeCircle selection without inferring ownership from names.
- The household picker now rejects an explicitly linked or currently active Person tracker when it is also selected as a separate person or pet. Fictional setup tests cover both exact links and confirm that identical display names without a link remain selectable. This validation uses HA's configured association and active `source` separately, never a name guess.
- A fictional malformed response for one Life360 member now leaves other member polls running. The affected tracker becomes unavailable after its own five-minute outage limit, diagnostics report `unexpected_response`, and a later valid response restores it. This is an adapter regression check, not a claim about a real Life360 API change.
- Fictional multi-Circle tests now cover one malformed member listing and one failed Circle listing during discovery. Previously known member links remain available for polling, healthy Circle members continue reporting, and discovery retries after one minute. A later complete response restores normal status. No real account was used for these failure cases.

## Open acceptance after this experimental prerelease

- Verify natural credential expiry when it occurs. Verify Home/Away departure and return later when the user can perform those movements. The disposable invalid-token check covers the rejection and repair path, while current live movement evidence remains limited to static report times.
- Keep the physical display check distinct from browser and synthetic evidence. Departure/return field tests were deferred by the user for this session.
- Perform an actual HACS UI upgrade after publication. The prepublication checks do not establish that HACS downloaded beta 11. The beta 11 ZIP has not been installed on the live server.
